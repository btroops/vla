# WSL2 下 MuJoCo 可视化：从 viewer 卡死到 meshcat 浏览器方案

- 日期：2026-11-23
- 来源：自己动手踩坑（W1 环境验收）；docs/07-仿真环境与工具链.md 的 7.6 / 7.7 / 7.8 节
- 状态：解决（meshcat 可用，viewer 放弃）

## 它解决什么问题

在 WSL2 里做 MuJoCo 仿真时，怎么"看到画面"。这看起来是个小问题，但踩下去才发现：物理跑得通不代表画面看得见，而画面是确认算法行为、调参数、交产物的前提。

## 我的理解（用自己的话）

MuJoCo 有两套"看"的方式：

1. **交互式窗口**（`mujoco.viewer.launch_passive`）：直接弹一个原生窗口，能用鼠标转视角。在原生 Linux 上最理想，但在 WSL2 上依赖 WSLg 把 OpenGL 从 Linux 转发到 Windows，这层转发和 GLFW 不对付，会卡死。
2. **离屏渲染**（`mujoco.Renderer`）：不弹窗，直接在内存里算出一帧图像（`numpy` 数组）。它不碰窗口系统，所以在 WSL 里稳如老狗。

关键认知：**`render ok` 只能证明渲染管线没问题，不能证明开窗没问题。** 这两件事走的是完全不同的系统路径——前者是纯计算，后者要跨 WSLg 的图形转发。所以离屏渲染通过了，开窗照样能崩。

离屏渲染再往前一步就是两条出路：把帧拼成 **gif 动画**（看运动过程，但不是交互）；或者用 **meshcat**——它在浏览器里渲染 3D，Python 端只负责发数据、不碰本地图形栈，所以能交互又不卡死。

类比：viewer 像是想在屋里直接开一扇真实的窗（要凿墙，墙是 WSLg，一凿就塌）；离屏渲染像是拍照片（不用开窗）；meshcat 像是架了个摄像头 + 网页直播（既能看又能转角度，还不用碰墙）。

## 核心机制

meshcat 的工作方式：Python 端启动一个服务器（默认 `127.0.0.1:7000`），把场景对象（球、网格）和位姿通过 zmq 发给浏览器；浏览器用 WebGL 渲染，鼠标交互也在浏览器端完成。WSL2 会把这个端口转发到 Windows，所以 Windows 浏览器能直连。

最小可用代码（红球上下落）：

```python
import time
import meshcat
import meshcat.geometry as g
import meshcat.transformations as tf

vis = meshcat.Visualizer()
vis["ball"].set_object(g.Sphere(0.2), g.MeshLambertMaterial(color=0xFF0000))

i = 0
while True:
    phase = (i % 100) / 100.0
    z = 1.0 - 0.9 * phase
    vis["ball"].set_transform(tf.translation_matrix([0, 0, z]))
    i += 1
    time.sleep(0.02)
```

运行后终端打印 `http://127.0.0.1:7000/static/`，在 Windows 浏览器打开即可。

## 踩坑记录（坑本格式）

### 坑 1：viewer 开窗闪退，WSL 会话整个崩掉

- 时间：2026-11-23
- 环境：WSL2 Ubuntu / Python 3.10 / mujoco 3.17.0 / RTX 4060 Laptop
- 现象：`mujoco.viewer.launch_passive` 开窗闪一下就退出，更糟的是终端提示符从 `btroops@...:~$` 变成了 `C:\Users\btroops>`——整个 WSL 会话被带崩，得在 PowerShell 里 `wsl --shutdown` 才能恢复。
- 我试过但没用：把循环从 500 步改成 `while viewer.is_running()`（以为是脚本跑完退出，不是）；`MUJOCO_GL=egl` / `osmesa`（没解决根本问题）。
- 真正的原因：WSLg 的 OpenGL 转发与 GLFW 兼容性差，开窗会触发图形栈崩溃。和代码无关。
- 解决办法：放弃 viewer，改用离屏渲染 + meshcat 浏览器方案。
- 耗时：约 1 小时
- 可避免性：中（一开始就该查 WSL2 + viewer 的已知问题，而不是先怀疑自己的代码）
- 以后怎么预防：在 WSL 里做仿真，默认就用离屏渲染或 meshcat，不碰原生窗口。

### 坑 2：离屏渲染成功但 gif 里没球

- 现象：用 `mujoco.Renderer` 渲染时 `render ok`、球心 z 值正常变化，但生成的 gif 只有默认网格和坐标轴，没有球。
- 原因：这是一次性误判——离屏渲染生成的 gif 本身是对的（帧里有球），真正没球的是 meshcat 页面：脚本 8 秒就跑完了，浏览器打开时服务器已关。
- 解决：把 meshcat 脚本改成无限循环，服务器常驻，再刷新浏览器，球就出来了。
- 耗时：约 10 分钟
- 教训：`render ok` 和"浏览器里看得见"是两回事；服务器进程的生命周期要和观察过程对齐。

### 坑 3：meshcat 页面只有网格，没有球

- 现象：浏览器能打开 `http://127.0.0.1:7000/static/`，能看到网格、坐标轴和 Controls 面板，但没有红球。
- 原因：脚本跑完退出，zmq 服务器关闭，浏览器只加载了默认的静态场景（网格），没收到球的数据。
- 解决：脚本改无限循环 + 刷新浏览器。
- 耗时：约 5 分钟
- 教训：看到页面 ≠ 连上了数据源。排查时先确认服务端进程还活着。

## 深入：WSLg 图形栈与 GLFW 的冲突（第一个"没懂的点"的答案）

核心结论先摆出来：**冲突发生在"窗口系统协议"这一层，不在"渲染计算"这一层。** 离屏渲染压根不碰窗口系统，所以完全绕开了。

### 两条路径的对比

MuJoCo 在这两种模式下分别走了什么路径：

**开窗（viewer）：**

```
Python 代码
  → GLFW 库请求创建一个"窗口"
  → 通过 Wayland 协议告诉 WSLg 的 compositor（Weston）"给我一块屏幕区域"
  → Weston 再通过微软的 RDP/WSLg 协议把画面送到 Windows 侧显示
  → Windows 的 DWM 把画面合成到桌面
  → 鼠标事件反向传回：Windows → RDP → Weston → Wayland → GLFW → Python
```

**离屏渲染（Renderer）：**

```
Python 代码
  → MuJoCo 内核算出像素（纯 CPU/GPU 计算）
  → 写进内存里的 numpy 数组
  → 结束
```

离屏渲染从头到尾**没有窗口、没有 compositor、没有跨系统传输**。它就是个数学计算，结果是一块内存。开窗则要跟一整套显示服务器打交道，而这套东西在 WSL2 里是个"翻译层叠翻译层"的脆弱结构。

### WSLg 的图形栈为什么脆

WSL2 本身没有真正的显示器，也没有传统的 X11 server。微软的方案是：

1. 在 WSL 里跑一个 **Weston compositor**（Wayland 显示服务器），提供一个虚拟显示
2. GPU 访问通过 **VirtIO GPU**（`/dev/dri`）转发到 Windows 的 GPU
3. Windows 侧用 **RDP 协议**把 Weston 的画面"投射"到一个窗口里

这套架构对"纯计算"很稳，但对"窗口管理协议"很脆。GLFW 创建窗口时要做的几件事，每一件都可能踩雷：

- **创建 surface**：GLFW 需要通过 Wayland 协议跟 Weston 申请一块可绘制区域，涉及一系列协议扩展（xdg-shell、EGL 的 wayland platform）。WSLg 的 Weston 实现未必支持所有扩展，版本稍有出入就协商失败。
- **绑定 OpenGL context**：GLFW 要创建一个 OpenGL context 并和 surface 绑定。这里 EGL 需要选对 platform（`EGL_PLATFORM_WAYLAND`），驱动（mesa 的 virtio_gpu / llvmpipe）要能配合。选错了就是黑屏或直接崩。
- **缓冲区交换**：每帧 `glSwapBuffers` 要把画好的帧交给 compositor 显示。WSLg 的 virtio GPU + RDP 转发在 buffer 同步上可能有竞态或不支持某些 present 模式——这正是"闪一下就崩"的典型时机。

### 为什么换 MUJOCO_GL=egl / osmesa 没用

`MUJOCO_GL` 这个环境变量只控制 **MuJoCo 离屏渲染用哪个后端**，也就是决定 `mujoco.Renderer` 那块内存怎么算出来。但 `mujoco.viewer` 走的是 GLFW 创建窗口的路径，它用的是系统 OpenGL（`libGL`）+ Wayland surface，**根本不读 `MUJOCO_GL` 这个变量**。所以换的是"照片怎么拍"，崩的是"窗怎么开"，两码事。

### 为什么离屏渲染绝对安全

离屏渲染（EGL surfaceless 或 OSMesa）做的事情：

- **EGL surfaceless**：创建一个**没有 surface 的 OpenGL context**，渲染目标直接是 FBO（Framebuffer Object，内存里的像素缓冲）。没有窗口、没有 compositor、没有协议协商。GPU 算完写内存，结束。
- **OSMesa**：连 GPU 都不用，纯 CPU 软件光栅化，结果直接写内存。更不可能碰显示系统。

这就是为什么自检 `render ok, frame= (64, 64, 3)` 那么顺畅——它本质上和跑 `numpy` 矩阵乘法一样，是个纯计算过程。

### meshcat 为什么又能交互

meshcat 的聪明之处在于**完全不碰本地窗口系统**：

```
Python 端：启动 zmq 服务器，发几何体数据和位姿
  → 网络（127.0.0.1:7000）
Windows 浏览器：收到数据，用 WebGL 渲染
  → 浏览器的窗口和交互由 Windows 原生管理
```

浏览器窗口是 Windows 的原生窗口，WebGL 渲染走的是 Windows 的 DirectX/OpenGL 驱动，鼠标事件也由 Windows 直接处理。WSL 这边只负责发数字，不碰任何图形 API。所以 WSLg 那套脆弱的转发层被彻底绕开了。

### 还没完全确定的部分

以上是基于 WSLg 架构的通用分析。具体到"这台机器上是哪一步崩的"，没有崩溃日志，只能推测最可能是 surface 创建或 buffer 交换环节。如果要精确定位，需要：

- 在 WSL 里运行 viewer 时 capture stderr（`MESA_DEBUG=1`、`EGL_LOG_LEVEL=debug` 等环境变量能打出更多日志）
- 看 Weston 的日志（`dmesg` 或 `journalctl`）

但这些对实际使用没帮助——反正结论是"这条路不通，换路"。

## 深入 2：meshcat 的 zmq 消息格式与浏览器端重建机制（第二个"没懂的点"的答案）

这次直接查了装在 `.venv` 里的 meshcat 0.3.2 源码，答案精确到文件。

### 整体链路（四段）

```
Python 端                     zmq 服务器进程              浏览器
Visualizer.set_transform()    ZMQWebSocketBridge         THREE.js Viewer
  → 构造命令对象      --REQ-->  → handle_zmq()   --WS-->   → handle_command_bytearray()
  → lower() 转 dict              → 更新 SceneTree             → msgpack.decode()
  → umsgpack.packb()             → forward_to_websockets()    → handle_command() 分发
```

注意有两个独立的端口（源码 `zmqserver.py:99-102`）：

- **zmq 端口默认 6000**：Python 客户端 ↔ 服务器进程（走 TCP，REQ/REP 模式）
- **web 端口默认 7000**：服务器 ↔ 浏览器（HTTP 静态文件 + WebSocket）

浏览器地址是 `http://127.0.0.1:7000/static/`，但 Python 发命令走的是 6000 端口——两个端口别搞混。

### 第 1 段：Python 端构造命令

源码 `meshcat/commands.py`。每条命令是一个类，`lower()` 方法把它转成 dict：

```python
# commands.py:34-45  SetTransform
def lower(self):
    return {
        "type": "set_transform",
        "path": self.path.lower(),
        "matrix": list(self.matrix.T.flatten())   # 4x4 矩阵转置后展开成 16 个数的 list
    }
```

`SetObject`（commands.py:5-31）的结构类似：`{"type": "set_object", "object": ..., "path": ...}`。其他命令还有 `delete`、`set_property`、`set_animation`、`capture_image`。

为什么要 `.T.flatten()`？因为 numpy 是行优先（row-major），而 JavaScript / WebGL 的矩阵约定是列优先（column-major），转置后展开正好对上。这是个容易踩的坑——如果你直接 `matrix.flatten()` 传过去，旋转会看起来是转置的。

### 第 2 段：zmq 发消息（3 帧 multipart）

源码 `meshcat/visualizer.py:56-63`：

```python
def send(self, command):
    cmd_data = command.lower()
    self.zmq_socket.send_multipart([
        cmd_data["type"].encode("utf-8"),   # 第 1 帧：命令类型字符串
        cmd_data["path"].encode("utf-8"),   # 第 2 帧：路径字符串，如 "meshcat/ball"
        umsgpack.packb(cmd_data)            # 第 3 帧：整个 dict 用 msgpack 序列化成二进制
    ])
    self.zmq_socket.recv()                  # 同步等服务器回 "ok"
```

几个关键点：

- **socket 类型是 `zmq.REQ`**（visualizer.py:40），服务器端是 `zmq.REP`（zmqserver.py:355）。这是严格的请求-应答模式：发一条必须等一条回复，不能连续发多条不等回包。
- **msgpack 是一种二进制序列化格式**，类似 JSON 但更紧凑、解析更快。`umsgpack` 是纯 Python 实现（就是安装时装的 `u-msgpack-python` 这个包）。二进制里包含 numpy 数组转换来的 list、嵌套 dict 等。
- **为什么发 3 帧而不是 1 帧**：前两帧是给服务器快速路由用的（type 和 path），服务器 `handle_zmq` 第一件事就是看第 1 帧决定走哪个分支（zmqserver.py:257），不需要先解包 msgpack。这是性能优化。
- **第 3 帧才是完整数据**，浏览器最终收到的就是这一帧——服务器原样转发，不重新编码。

### 第 3 段：服务器做两件事

源码 `meshcat/servers/zmqserver.py:256-296` 的 `handle_zmq()`：

1. **转发给所有浏览器**（`forward_to_websockets`，zmqserver.py:349-352）：把第 3 帧（msgpack 二进制）通过 WebSocket `binary=True` 广播给 `websocket_pool` 里每个连接。
2. **更新内存里的场景树 `SceneTree`**（按 path 索引的树结构，zmqserver.py:236）：`set_transform` 就更新对应节点的 transform，`set_object` 更新 object，`delete` 删节点。

这里有个值得记的优化：**object 缓存**（zmqserver.py:273-277）。如果收到的是 `set_object` 且新对象的二进制数据和旧的一模一样，就跳过广播——避免每帧重复发同一个静态网格。

场景树 `SceneTree` 的存在正好解释了之前的坑 3：浏览器新连上来时，服务器会调 `send_scene()`（zmqserver.py:361-370）把树里所有节点重放一遍。如果服务器进程死了，树就没了，新浏览器自然只看到默认网格。

### 第 4 段：浏览器端解析与重建

源码 `meshcat/viewer/src/index.js`（这是 Webpack 之前的原始 JS，编译后在 `viewer/dist/main.min.js`）：

```javascript
// index.js:1066-1080
handle_command_message(message) {
    this.handle_command_bytearray(new Uint8Array(message.data));
}
handle_command_bytearray(bytearray) {
    let decoded = msgpack.decode(bytearray);   // 用 JS 版 msgpack 库解码成对象
    this.handle_command(decoded);
}
connect(url) {
    url = `ws://${location.host}`;             // 默认连当前主机的 WebSocket
    this.connection = new WebSocket(url);
    this.connection.binaryType = "arraybuffer";
    this.connection.onmessage = (msg) => this.handle_command_message(msg);
}
```

`handle_command()`（index.js:1025-1059）是个 switch 式的分发器，按 `cmd.type` 处理：

- `set_transform` → `this.set_transform(path, cmd.matrix)`：找到场景树里对应 path 的节点，设置它的 4x4 变换矩阵
- `set_object` → `this.set_object_from_json(path, cmd.object)`：根据 JSON 描述创建 THREE.js 的几何体和材质，挂到场景树对应节点
- `delete` → 删除路径节点
- `set_property` / `set_animation` / `capture_image` 等同理

重建场景的核心在 `set_object_from_json`：它读 `cmd.object` 里的几何体描述（比如 `{"type": "SphereGeometry", "radius": 0.2}` 之类），调用对应的 THREE.js 构造器（`new THREE.SphereGeometry(0.2)`）生成实际几何体，再加上材质，挂进 THREE.js 的 `Scene`。之后 THREE.js 自己的渲染循环（`requestAnimationFrame`）负责每帧把场景画到 canvas 上——这部分完全在浏览器里跑，Python 端不参与。

### 用一句话串起来

**Python 端把"做什么、对谁做、参数是什么"打包成 msgpack 二进制，经 zmq 发给服务器；服务器原样广播给浏览器，同时在内存里维护一份场景树供新连接重放；浏览器解码后按 type 分发，用 THREE.js 构造或更新对应的 3D 对象，剩下的渲染和交互由浏览器全权负责。**

这也解释了 meshcat 为什么能绕开 WSLg：WSL 里跑的 Python 只发数字（zmq），浏览器里跑的 JS 才碰图形 API（WebGL），两边通过 WebSocket 隔着一个进程边界。

## 深入 3：真实机械臂模型（URDF/MJCF）能不能直接接进 meshcat（第三个"没懂的点"的答案）

查了 meshcat 0.3.2 的 `geometry.py` 和浏览器端 `index.js` 源码，结论：

**没有一键桥接。meshcat 不认识 MJCF/URDF 这种模型文件格式，必须自己遍历模型的 geom，逐个转成 meshcat 的几何体，再每个仿真步同步位姿。** 但转换没想象中难，因为 meshcat 原生支持常见的几何体类型和网格文件格式。

### meshcat 原生支持什么（geometry.py）

基本几何体（直接有类）：

- `Box(lengths)` → 浏览器端 `BoxGeometry`
- `Sphere(radius)` → `SphereGeometry`
- `Cylinder(height, radius, ...)` → `CylinderGeometry`（按 Three.js 约定，旋转对称轴是 y 轴）
- `TriangularMeshGeometry` → 直接用顶点/面数据构造

网格文件（通过 `MeshGeometry` 系列，geometry.py:383-448）：

- `ObjMeshGeometry.from_file(path)` → OBJ
- `DaeMeshGeometry.from_file(path)` → DAE（Collada）
- `StlMeshGeometry.from_file(path)` → STL（二进制用 msgpack Ext 包装）

浏览器端 `index.js:86-115` 的 `handle_special_geometry` 负责把这些 `_meshfile` 类型用对应的 JS 加载器（OBJLoader2 / ColladaLoader / STLLoader）解析成 Three.js 几何体。**注意它不认 MJCF/URDF 的 XML**——所以 MuJoCo 模型文件本身发过去没用。

### 正确的接入思路（分两步）

**第一步：初始化时把 MuJoCo 的每个 geom 转成 meshcat 对象**

MuJoCo 的模型加载后，`model.geom_type[i]` 告诉你第 i 个 geom 是什么类型，`mujoco.mjtGeom` 枚举里有：

- `mjGEOM_SPHERE` → `meshcat.geometry.Sphere(model.geom_size[i][0])`
- `mjGEOM_BOX` → `meshcat.geometry.Box(2 * model.geom_size[i])`（注意 MuJoCo 的 size 是半长，Three.js 的 BoxGeometry 要全长，所以乘 2）
- `mjGEOM_CYLCYLINDER` → `meshcat.geometry.Cylinder(...)`
- `mjGEOM_CAPSULE` → 胶囊体没有直接对应，可用 Cylinder + 两个 Sphere 组合近似
- `mjGEOM_MESH` → 这个最关键：MuJoCo 的 mesh 数据在 `model.mesh_vert` / `model.mesh_facets` 里（顶点和面），可以提取出来用 `TriangularMeshGeometry` 构造，或者导出成 STL/OBJ 再用 `StlMeshGeometry.from_file`
- `mjGEOM_PLANE` → Three.js 的无限平面，可用一个大的 `Box` 近似

每个 geom 放到 meshcat 场景树的一个 path 下，比如 `vis["robot"]["link1"]["geom0"]`。

**第二步：每个仿真步同步位姿**

MuJoCo 里 `data.geom_xpos[i]`（世界坐标位置）和 `data.geom_xmat[i]`（3x3 旋转矩阵，行优先）给出了每个 geom 的当前位姿。拼成 4x4 齐次变换矩阵：

```python
import numpy as np

T = np.eye(4)
T[:3, :3] = data.geom_xmat[i].reshape(3, 3)
T[:3, 3] = data.geom_xpos[i]
vis["robot"]["link1"][f"geom{i}"].set_transform(T)
```

`set_transform` 内部会做 `.T.flatten()`（前面查过源码），正好对上 WebGL 的列优先约定。

### 关键坑（提前记下来）

1. **坐标约定**：MuJoCo 默认 z 轴向上，Three.js 默认 y 轴向上。如果模型直接搬过去会"躺倒"。要么在初始化时给整个场景根节点加一个旋转（-90° 绕 x 轴），要么在每个 geom 的变换里处理。
2. **Mesh 顶点数据**：MuJoCo 的 `mesh_facets` 存的是三角形索引，`TriangularMeshGeometry` 需要 `(vertices, faces)` 格式，索引要对得上。
3. **材质/颜色**：MuJoCo 的 `model.geom_rgba[i]` 是 RGBA 浮点（0-1），meshcat 的材质 color 要 `0xRRGGBB` 整数，需要转换：`int(r*255)<<16 | int(g*255)<<8 | int(b*255)`。
4. **性能**：每个 geom 每帧一次 `set_transform`，走 zmq + WebSocket。几十个 geom 没问题，几百个会掉帧。 ROBOT 模型通常 10-30 个 link，可以接受。
5. **有没有现成轮子**：搜过 pip 包，有个 `pinocchio` 的 `pinocchio.visualize.MeshcatVisualizer` 能把 pinocchio 加载的 URDF 显示到 meshcat，但它走的是 pinocchio 的模型解析，不接受 MuJoCo 的 MJCF。对 MuJoCo 模型还是得自己写转换循环。**如果以后要反复用，可以把这套转换封装成一个 `mujoco_meshcat_bridge.py` 放进 `projects/` 里复用。**

### 一句话总结

meshcat 能显示 OBJ/DAE/STL 网格文件和基本几何体，但不认识 MJCF/URDF 模型描述。接真实机械臂要自己写个"翻译层"：初始化时把每个 geom 按类型转成 meshcat 对象，每帧用 `geom_xpos` + `geom_xmat` 同步位姿。这套逻辑写一次就能复用。

## 实战：把真实 MuJoCo 仿真接进 meshcat（已完成）

代码在 `projects/P00-mujoco-meshcat-visualization/src/mujoco_meshcat_bridge.py`：场景是地面 + 静止蓝盒子 + 自由落体的红球，遍历所有 geom 按类型转成 meshcat 对象，每帧用 `geom_xpos`/`geom_xmat` 同步位姿。浏览器里能看到红球真实落地（MuJoCo `mj_step` 算的物理），不再是手写数学的假球。

### 这一步踩的三个坑

**坑 A：`geom_xmat` 初始化时全零。** MjData 刚创建时 `geom_xmat` / `geom_xpos` 全是 0，必须先调一次 `mujoco.mj_step(model, data)` 才有真实位姿。所以初始化循环前要先 step 一次。

**坑 B：z-up → y-up 不能只转父节点。** 第一版代码给一个父节点设了 z-up→y-up 旋转，以为子节点会继承。结果地面变成一堵竖直的墙。原因：meshcat 的 `set_transform` 直接设**世界坐标**位姿，不叠加父节点的变换。修复：把 `ZUP_TO_YUP @ T_mujoco` 直接乘进每个 geom 的位姿里。

**坑 C：一度以为默认相机贴着地面，手写法灯反而更差。** 早期以为 meshcat 默认相机贴地（本地 `(3,1,0)` 经父节点 `R_x(90°)` → 世界约 (3,0,1)），于是写了 look-at 矩阵 + `inv(R_parent)` 想手动设斜俯视。结果视角几乎平视（网格像墙）——因为 eye 只比 target 高 1，俯角才 13°。**最终发现：smoke 脚本完全没设相机，默认视角反而是漂亮的斜上方俯视。** 正确做法：删掉所有相机代码，用 meshcat 默认视角。手写的相机版本备份在 `projects/P00-mujoco-meshcat-visualization/src/mujoco_meshcat_bridge_user.py` 作对照。

### 颜色与尺寸转换（顺带记下）

- MuJoCo `geom_rgba` 是 0-1 浮点，meshcat 材质要 `0xRRGGBB` 整数：`(int(r*255)<<16) | (int(g*255)<<8) | int(b*255)`
- MuJoCo `geom_size` 是半长，meshcat `Box(width,height,depth)` 要全长：乘 2
- `geom_xmat` 是 9 元素，要 `.reshape(3,3)` 再拼进 4x4 矩阵

**坑 D：落体场景"静止"的错觉。** 第一版用自由落体球，0.55 秒就落地停住——打开浏览器时早就不动了，看起来像没同步。换成带铰链 + 初始角速度的摆（`data.qvel[0] = 3.0`），阻尼很小，随时打开都在摆动。**教训：验证"动起来"要用持续运动的系统，别用一次性落体。**

**坑 E：相机设置的正确结论。** meshcat 相机在浏览器场景树的根路径 `Cameras/default/rotated/<object>`，不在默认 `meshcat` 子树下（`path.py:9-13` 里空字符串重置到根，所以 Python 端要写 `vis["/Cameras/default/rotated/<object>"]`）。但更重要的是：**默认相机本来就是精心调好的斜俯视，不需要设。** 手动设要同时处理父节点旋转（`inv(R_parent)`）、look-at 矩阵、俯角——极易搞差。验证过程：smoke 脚本零相机代码 → 视角漂亮；手写 look-at（eye 高度差 1，俯角 13°）→ 网格像墙；删掉相机代码 → 恢复到 smoke 的好视角。**结论：不要设相机，默认就够好；如果场景特殊必须设，把 eye 抬到 target 上方 2-3 个单位保证俯角够大。**

### 已验证可用的最终配置
