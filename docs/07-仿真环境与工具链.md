## 正文

### 7.1 为什么研究离不开仿真

**直觉**：教机器人做事像教人学骑车。真车只有一辆，摔一次修三个月；仿真是一台「可以无限次摔坏」的车。真机还卡在样本效率上：现代强化学习（Reinforcement Learning, RL）动辄需要百万级交互回合，真机按 10 Hz 控制、一天跑满 8 小时也只有几十万步，还得有人盯着。所以正确分工是 **sim-to-real**：仿真里大规模迭代、真机上少量验证，并从第一天起加噪声与随机化（domain randomization）。仿真给了五件真机给不了的东西：

1. **便宜**：一次碰撞的代价是几毫秒 CPU 时间，而不是一张维修工单。
2. **快**：物理时间可以比墙钟时间快很多倍，也能慢放看细节。
3. **可大规模并行**：GPU 上同时开成百上千个环境实例，采样速度近似「实例数 × 步频」。
4. **可复现**：固定随机种子与初始状态，同一条轨迹能逐帧重放对比。
5. **能测危险工况**：撞墙、跌落、被猛推、传感器断线——真机上不敢做，仿真里是标准测试项。

**但仿真替代不了四类东西**，这就是 reality gap（现实鸿沟）：

- **物理参数偏差**：摩擦系数、质量分布、电机响应、通信延迟，仿真里都是你手填的数，真机上都是你不知道的数。
- **接触与柔性**：软物体、线缆、布料仍是难题；夹爪捏鸡蛋时「捏碎」与「捏住」在仿真里往往只差几个参数。
- **真实传感器噪声**：运动模糊、过曝、深度图空洞、镜头畸变、标定误差、时间戳不同步——仿真相机通常「太干净」。
- **人的因素**：人机协作中的意图与犹豫，以及遥操作演示者手上的「手感」，都很难建模。

### 7.2 物理引擎横向对比

物理引擎（physics engine）在每个时间步里算「谁碰了谁、受多大力、下一步在哪」。差别不在「会不会算牛顿定律」，而在**为谁优化**：接触稳定、一键跑通、GPU 上万的并行，还是某个社区生态。

| 引擎 | 定位 | 擅长 | 短板 | 典型用户 | 入门难度 |
| --- | --- | --- | --- | --- | --- |
| **MuJoCo** | 通用刚体 + 接触动力学引擎，MJCF 格式，现由 Google DeepMind 维护并开源 | 接触与连续动力学成熟稳定、速度快、API 干净、单机可用 | 原生不做 GPU 大规模并行；渲染「够用」而非照片级 | 腿足/操作控制、RL 研究论文的常见选择 | 低（`pip install mujoco`） |
| **PyBullet** | 基于 Bullet 引擎的 Python 接口 | 极易上手、教程与旧代码多、安装无痛 | 生态偏旧、接触与摩擦精度一般、活跃度一般 | 教学、老论文复现、快速原型 | 极低 |
| **Isaac Sim / Isaac Lab** | 基于 NVIDIA Omniverse 的仿真平台，Isaac Lab 是其上的 RL 框架 | GPU 大规模并行、渲染逼真、传感器仿真丰富 | 对 NVIDIA RTX 级显卡与驱动要求高、包体巨大、迭代快 | 大规模并行 RL、合成数据 | 高 |
| **Gazebo** | 老牌机器人仿真器，ROS 生态默认搭档 | 与 ROS 集成成熟、移动机器人/多机器人、传感器插件生态 | 操作与接触精度一般；Gazebo Classic 已进入停止维护阶段，新项目应用新版 Gazebo（曾名 Ignition），以官方文档为准 | ROS 教学、移动机器人、SLAM 与导航 | 中 |
| **SAPIEN / ManiSkill** | 面向操作任务的仿真与 benchmark 套件 | 高质量渲染、丰富操作任务与示范数据 | 通用性不如 MuJoCo，生态集中在操作方向 | 操作策略学习、模仿学习、VLA 评测 | 中 |

- **新引擎只点名**：近年出现了 **Genesis**、**Newton**（NVIDIA、Google DeepMind 等联合推动的开源物理引擎）一类项目，主打 GPU 并行等方向。它们**仍在快速演进，接口与能力边界都可能变，一切以官方文档为准**，新手不建议把学习路径押在上面。

### 7.3 机器人描述格式：URDF 与 MJCF

**一句话区分**：**URDF**（Unified Robot Description Format，ROS 生态的 XML 格式）偏「描述机器人**是什么**」——有哪些连杆、怎么连、能动多少；**MJCF**（MuJoCo XML Format）偏「描述仿真**场景怎么算**」——除机器人外还有地面、光照、求解器参数、接触参数、执行器。URDF 的骨架只有两种元素，其余都是它们身上的属性：

```xml
<robot name="two_link">
  <link name="base_link">
    <inertial>   <!-- 质量与惯量：决定动力学 -->
      <mass value="1.0"/><inertia ixx="0.01" ixy="0" ixz="0" iyy="0.01" iyz="0" izz="0.01"/>
    </inertial>
    <visual>     <!-- 只影响渲染 --><geometry><box size="0.1 0.1 0.1"/></geometry></visual>
    <collision>  <!-- 只影响物理 --><geometry><box size="0.1 0.1 0.1"/></geometry></collision>
  </link>
  <!-- 子连杆 link1 定义类似，此处省略 -->
  <joint name="joint1" type="revolute">
    <parent link="base_link"/><child link="link1"/>
    <origin xyz="0 0 0.1" rpy="0 0 0"/>   <!-- 相对父连杆的位姿 -->
    <axis xyz="0 0 1"/><limit lower="-1.57" upper="1.57" effort="10" velocity="1.0"/>
  </joint>
</robot>
```

`link` 是刚体；`joint` 连接两个刚体（`revolute` 转动、`prismatic` 移动、`fixed` 固定、`floating` 自由）；`inertial` 决定「推它一下怎么动」；`visual` 决定「镜头里什么样」；`collision` 决定「撞上去会怎样」。MJCF 更「场景化」：

```xml
<mujoco model="two_link">
  <compiler angle="radian"/><option timestep="0.002" integrator="implicitfast"/>
  <worldbody>
    <geom type="plane" size="1 1 0.1"/>
    <body name="link1" pos="0 0 0.1">
      <joint name="joint1" type="hinge" axis="0 0 1" range="-1.57 1.57"/>
      <geom type="capsule" fromto="0 0 0 0 0 0.2" size="0.02"/>
    </body>
  </worldbody>
  <actuator><motor joint="joint1" ctrlrange="-10 10"/></actuator>
</mujoco>
```

**为什么碰撞体常被简化成简单几何？** 碰撞检测开销随几何复杂度快速增长。外观用几万面片的网格、碰撞用一个圆柱或几个盒子近似，是行业标准做法。代价是碰撞体不准，抓取与接触的仿真会偏——这正是 reality gap 的一大来源。

**转换工具与坑**：MuJoCo 本身能直接解析 URDF（内部转 MJCF），社区有 `urdf2mjcf` 之类的脚本，Isaac Sim 有 URDF Importer，PyBullet 也能加载 URDF。但转换几乎总会掉东西：`gazebo` 扩展标签里的摩擦与自碰撞开关可能丢失；惯量矩阵缺失或非正定（CAD 导出常见）会让仿真爆炸或飘走；`limit`、`damping`、`armature`（电机转子惯量）两边语义不完全一致；单位与 `rpy` 约定错了会让机器人「躺平」。实操：转完先用 viewer 看一眼——站不站得住、关节能不能转、有没有穿模。

### 7.4 ROS / ROS 2 入门

- **节点（node）**：一个进程干一件事。相机驱动、路径规划、日志记录各是一个节点。
- **话题（topic）**：单向、异步、多对多广播，适合「一直往外发」的数据流（图像、关节状态、里程计）。
- **服务（service）**：请求—应答、同步、一问一答，适合「查一下电量」这类短操作。
- **动作（action）**：长任务的请求—反馈—结果三段式，可中途取消，适合「移动到那个位置」。
- **launch**：用一个文件把一堆节点和参数一起启动，相当于给整机系统写 compose 文件。
- **tf2**：坐标变换树。基座、各连杆、相机、世界坐标系都是树上节点，tf2 维护「谁相对谁在哪」并带时间戳。

**ROS 的正确定位是「胶水」**：它不是操作系统也不是算法库，而是**通信中间件 + 一堆约定俗成的工具**（像一个公司内部的消息系统 + 文件夹规范），让不同语言、团队、年代的模块拼在一起。它不帮你算动力学，也不帮你训练策略。很多 RL / VLA 项目绕开它，原因很实际：依赖重（完整发行版体积不小且绑定特定 Ubuntu 版本，和 CUDA、PyTorch 约束叠加容易冲突）；调试链路长（一次推理要经过「Python 进程 → 序列化 → DDS 传输 → 反序列化 → 驱动」）；而 Python 直接调物理引擎更顺，`env.step()` 一行推进一个时间步。常见实践是「训练在纯 Python + Gymnasium，部署在 ROS 2 或厂商 SDK」。

### 7.6 环境搭建指引

**一个项目一个环境**：用 conda / mamba（或更轻量的 uv）给每个项目建独立环境。机器人项目版本极其敏感，PyTorch、CUDA、MuJoCo、ROS 互相牵扯，全局装一次迟早打架。

```bash
conda create -n vla-sim python=3.10 -y && conda activate vla-sim
pip install mujoco gymnasium
# 或用 uv（更快）：uv venv --python 3.10 .venv && source .venv/bin/activate && uv pip install mujoco gymnasium
```

**CUDA 与 PyTorch 的版本匹配**：不要背版本号，去查表。先看 `nvidia-smi` 右上角的 `CUDA Version`（这是驱动支持的上限，不是已安装版本），再去 PyTorch 官网 Get Started / Previous Versions 页面选对应安装命令，装完用 `torch.cuda.is_available()` 验证。这一步没过，后面所有 GPU 训练都是白搭。

**Isaac Lab 的门槛**：基于 Isaac Sim 与 Omniverse，需要 **NVIDIA RTX 级显卡与较新驱动**，对 Ubuntu / Python 版本也有要求，官方通常推荐原生 Linux。**具体硬件与系统要求以官方文档为准**。用核显或 AMD 显卡的话，先用 MuJoCo 把算法跑起来，别在装环境上耗一周。

下面五个是最常见的踩坑：

1. **无头服务器渲染黑屏 / 报 GL 错误**：没显示器的机器上 OpenGL 需要离屏后端，常见解法是启用 EGL 或 OSMesa，或用虚拟显示（`xvfb-run`）；MuJoCo 也可用 `MUJOCO_GL` 指定后端。渲染坑九成出在这里。
2. **路径含中文或空格导致编译失败**：C++ 扩展、CMake、资源加载器对非 ASCII 路径支持很差。项目放纯英文无空格路径，能省掉大量莫名错误。
3. **WSL 与原生 Linux 的差异**：WSL 2 通过 WSLg 支持 GUI、CUDA 也能直通，但图形栈、跨 `/mnt/c` 的文件性能（极慢）、部分离屏渲染行为都与原生不同。训练脚本放 WSL 内部文件系统（如 `~/`）。
4. **conda 装 mujoco 后渲染黑屏**：conda 渠道二进制可能链接到不同的 GL/驱动库，或与 pip 版版本不一致。排查：换纯 pip 版重装 → 检查 `MUJOCO_GL` → 确认有 `libEGL`。
5. **pip 与 conda 混装导致动态库冲突**：典型症状是 `ImportError: libXXX.so: cannot open shared object file` 或段错误。原则是同一个包只从一个渠道装；PyTorch 生态优先官方 pip 源，`libgl1`、`libegl1` 这类系统依赖用 apt。

```python
"""仿真环境自检（每换一次环境跑一遍）：python check_env.py"""
import platform
import sys


def main() -> None:
    ver = platform.python_version() + ("" if sys.version_info[:2] >= (3, 10) else "（建议 >= 3.10）")
    print(f"[python] {ver}")

    try:
        import torch
        print(f"[torch] {torch.__version__}, cuda={torch.cuda.is_available()}")
        if torch.cuda.is_available():
            print(f"[torch] build={torch.version.cuda}, gpu={torch.cuda.get_device_name(0)}")
    except ImportError:
        print("[torch] 未安装（只跑 MuJoCo 可先忽略）")

    try:
        import mujoco
    except ImportError:
        print("[mujoco] 未安装")
        return
    print(f"[mujoco] {mujoco.__version__}")

    xml = """<mujoco><worldbody>
      <light pos="0 0 1" dir="0 0 -1"/>
      <geom type="plane" size="1 1 0.1"/>
      <body pos="0 0 0.5"><joint type="free"/><geom type="sphere" size="0.05"/></body>
    </worldbody></mujoco>"""
    model = mujoco.MjModel.from_xml_string(xml)
    data = mujoco.MjData(model)
    for _ in range(10):
        mujoco.mj_step(model, data)
    print(f"[mujoco] step ok, 球心 z={data.qpos[2]:.4f}")

    try:  # 离屏渲染一帧，验证 EGL / OSMesa 是否可用
        renderer = mujoco.Renderer(model, height=64, width=64)
        renderer.update_scene(data)
        frame = renderer.render()
        renderer.close()
        print(f"[mujoco] render ok, frame={frame.shape}")
    except Exception as exc:  # noqa: BLE001
        print(f"[mujoco] render FAILED: {exc} -> 需要 EGL/OSMesa 或 xvfb-run")


if __name__ == "__main__":
    main()
```

**验收标准**：最后出现 `render ok`。只有 `step ok` 而 render 失败，说明物理没问题、图形栈没配好——训练可能还能跑，但要画面的事情都会卡住。

### 7.7 实验管理与可复现性

- **固定随机种子**：至少固定 `random`、`numpy`、`torch`，并把种子值记进日志。GPU 上部分算子即使固定种子也不保证逐位复现，能复现到「同分布内一致」就算合格。
- **配置化**：超参数、路径、模型名全写进 YAML，用 **Hydra** 一类工具管理多组实验。**别用「改代码里的常量」做实验。**
- **日志**：用 **TensorBoard** 或 **wandb** 记录损失、成功率与视频片段。只记数字不录像等于丢掉一半信息——「怎么失败的」比「失败率多少」更重要。
- **checkpoint**：权重 + 优化器状态 + 训练步数 + 配置快照，四样一起存；每次实验写一两句人话备注（改了奖励哪一项、加了哪种噪声）。
可复现性清单（提交结果前自查）：

- [ ] 环境版本已锁定（`pip freeze` / `conda env export` 存档）
- [ ] 随机种子写进配置并在日志里打印
- [ ] 数据集版本或哈希已记录
- [ ] 配置文件与代码 commit 一起保存
- [ ] 训练日志与评测脚本可一键重跑
- [ ] 指标定义写清楚（成功率怎么算、几次成功算一次）
- [ ] 至少从头重跑过一次，得到同量级结果
- [ ] 硬件信息（GPU 型号与数量）已记录

### 7.8 新手跑通第一个仿真：最短路径

1. **装环境**：建干净环境，`pip install mujoco`。验收：`python -c "import mujoco; print(mujoco.__version__)"` 打印出版本号。
2. **跑自检脚本**：把 7.6 的 `check_env.py` 跑一遍。验收：`step ok` 与 `render ok` 都出现。
3. **打开官方模型**：加载 MuJoCo 自带示例模型并用 `mujoco.viewer.launch_passive` 开窗。验收：窗口里出现机器人，且能动。
4. **自己写最小模型**：手写一个单摆或自由落体小球的 XML。验收：窗口里出现一个摆动的小球，物理上「像那么回事」。
5. **接上 Gymnasium**：用自带 `Pendulum-v1` 跑 `reset` / `step` 循环。验收：能打印 `obs` 形状与每步 `reward`。
6. **训练最傻的基线**：用 Stable-Baselines3 的 PPO 在 `Pendulum-v1` 上训几分钟。验收：回报曲线明显上升（哪怕很小）。

走完这六步，你就有了「换引擎、换任务、换算法」的基本盘。

## 动手练习

### 练习一：MuJoCo 最小可运行示例

保存为 `swing.py` 运行。用到的是真实 API：`mujoco.MjModel.from_xml_path`、`mujoco.MjData`、`mujoco.mj_step`、`mujoco.viewer.launch_passive`。

```python
import time
import mujoco.viewer  # 同时绑定 mujoco 包

XML = """<mujoco>
  <option timestep="0.002"/>
  <worldbody>
    <light pos="0 0 2" dir="0 0 -1"/>
    <geom type="plane" size="2 2 0.1"/>
    <body name="pole" pos="0 0 1">
      <joint name="hinge" type="hinge" axis="0 1 0"/>
      <geom type="capsule" fromto="0 0 0 0 0 -0.5" size="0.02"/>
    </body>
  </worldbody>
</mujoco>"""

with open("pendulum.xml", "w", encoding="utf-8") as f:
    f.write(XML)

model = mujoco.MjModel.from_xml_path("pendulum.xml")   # 编译模型
data = mujoco.MjData(model)                            # 存运行时状态

with mujoco.viewer.launch_passive(model, data) as viewer:
    while viewer.is_running():
        mujoco.mj_step(model, data)   # 推进一个物理时间步
        viewer.sync()                 # 把新状态推给渲染窗口
        time.sleep(model.opt.timestep)
```

### 练习二：Gymnasium 基本循环

**关键细节**：新版 Gymnasium 的 `reset()` 返回 `(obs, info)` 二元组，`step()` 返回 `(obs, reward, terminated, truncated, info)` 五元组。网上大量老教程还是四元组，照抄会直接报错。

```python
import gymnasium as gym

env = gym.make("Pendulum-v1")
obs, info = env.reset(seed=42)                                 # 两个返回值
print("obs shape:", obs.shape, env.action_space)
total = 0.0
for _ in range(200):
    action = env.action_space.sample()                         # 换成策略输出
    obs, reward, terminated, truncated, info = env.step(action) # 五个返回值
    total += reward
    if terminated or truncated:
        obs, info = env.reset()
env.close()
print("随机策略总回报:", round(total, 2))
```

## 常见误区

1. **新手常以为「仿真里跑通了就等于真机能用」，其实是仿真只是必要条件。** 摩擦、延迟、相机噪声、标定误差都不在仿真里，差的往往不止一点点。
2. **新手常以为「物理引擎越快越好」，其实是稳定性与准确性优先。** 算出「机器人穿过地面」的引擎再快也没用；时间步、接触参数、积分器比吞吐量更决定结果能否用。
3. **新手常以为「URDF 转 MJCF 一键就行」，其实是转换只搬结构，参数几乎总要手工补。** 惯量、阻尼、碰撞体、执行器往往得重写。
4. **新手常以为「用了 ROS 才是正经机器人项目」，其实是 ROS 是部署期的胶水，不是训练期的必需品。** 算法阶段用纯 Python + Gymnasium 效率高得多。
5. **新手常以为「设了随机种子就能完全复现」，其实是还要锁定环境版本、数据版本与硬件配置。** GPU 算子、多线程顺序、库版本变化都会让结果漂移。

## 自测题

**1. 「仿真便宜」到底便宜在哪？举一个真机代价极高、仿真里却应反复做的测试场景。**

<details><summary>点击查看答案</summary>
单次交互的边际成本趋近于零：没有硬件损耗、没有场地与人力占用，失败一次只是几十毫秒计算。典型场景是「故意失败测试」——高速撞墙、从桌边跌落、相机关键时刻断线，用来验证安全层与恢复策略；真机上做意味着维修成本与人身风险。
</details>

**2. 要做 GPU 大规模并行强化学习训练四足，优先哪个引擎？只验证抓取的接触逻辑呢？**

<details><summary>点击查看答案</summary>
前者优先 Isaac Lab（基于 Omniverse），核心优势是成千上万环境并行，匹配大规模 RL 的采样需求，代价是显卡与驱动门槛高。后者优先 MuJoCo：接触与连续动力学成熟、单机可用、`pip` 一行装好。判断标准是「瓶颈在采样量还是在接触精度」。
</details>

**3. 为什么碰撞体常是简单几何而视觉模型是精细网格？代价是什么？**

<details><summary>点击查看答案</summary>
碰撞检测开销随几何复杂度快速增长，渲染则对精度不敏感（GPU 擅长画三角面片），所以视觉用高模、碰撞用低模是标准折中。代价是接触几何与实际外形不符，抓取、插入、堆叠这类依赖接触细节的任务会偏差。
</details>

**4. ROS 2 的话题、服务、动作各适合什么？为什么 VLA 训练项目常常不用 ROS？**

<details><summary>点击查看答案</summary>
话题是单向异步广播，适合连续数据流；服务是同步一问一答，适合短查询；动作是带反馈、可取消的长任务。不用 ROS 是因为依赖重、版本耦合强、跨进程调试链路长，而 Python 直接调物理引擎更简单高效；ROS 更适合部署期集成真实硬件。
</details>

**5. 同事说「设了随机种子，结果一定能复现」，哪里不严谨？**

<details><summary>点击查看答案</summary>
种子只控制伪随机序列，不控制系统性差异。补强措施：锁定并记录依赖版本；记录数据集版本或哈希；记录 GPU 型号与数量（非确定性算子带来数值漂移）；配置与代码 commit 一同保存；保留至少一次从头重跑的证据。
</details>
